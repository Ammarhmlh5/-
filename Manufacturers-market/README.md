# السوق الحرة

## التعريف

السوق الحرة هو نظام إلكتروني مستقل ومتكامل مع ERPNext، مخصص لإدارة العلاقة التجارية والتشغيلية مع الموردين في الصين. يعمل النظام كامتداد للمشروع الرئيسي، لكنه يحتفظ بقاعدة بيانات وخدمات مستقلة، ولا يتصل مباشرة بقاعدة بيانات ERPNext.

الهدف من النظام هو تنظيم الموردين والمنتجات والأسعار والمخزون والطلبات، ثم تمرير العمليات المالية أو الرئيسية إلى ERPNext من خلال قناة التكامل المعتمدة.

## موقع السوق ضمن المنظومة

تتكون المنظومة من ثلاثة أجزاء مترابطة:

1. **ERPNext:** النواة المحاسبية والمرجع المالي الرئيسي.
2. **نظام الشحن:** يدير العملاء والشحنات والعمليات اللوجستية، وينشئ كيانات العملاء في ERPNext.
3. **السوق الحرة:** يدير الموردين الصينيين والكتالوج والطلبات التجارية، وينشئ كيانات الموردين في ERPNext.

السوق الحرة لا يحل محل ERPNext، ولا ينفذ استعلامات مباشرة على قاعدة بياناته. جميع العمليات التي تحتاج إلى ERPNext تمر عبر خدمة التكامل المركزية.

## ما يقوم به السوق

### 1. إدارة الموردين الصينيين

- تسجيل الموردين المتعاقد معهم.
- حفظ بيانات الشركة وبيانات الاتصال والعملة ومرجع العقد.
- تفعيل أو تعطيل المورد.
- ربط المورد المحلي بكيان `Supplier` في ERPNext.
- إنشاء كيان المورد في ERPNext عند اعتماد المورد لأول مرة.
- حفظ رقم ERPNext محلياً لمتابعة المزامنة ومنع التكرار.

### 2. إدارة المنتجات والكتالوج

- إنشاء المنتجات وربطها بالمورد الصحيح.
- إدارة SKU واضح لكل منتج أو إصدار.
- حفظ الاسم والوصف والوزن والحجم.
- حفظ سعر المصنع باليوان الصيني.
- إدارة المخزون المتاح.
- منع عرض أو بيع المنتجات غير النشطة.
- عرض السعر النهائي للعميل بعد احتساب سعر الصرف والرسوم من الخادم.

### 3. إدارة الأسعار والعملات

- استقبال سعر الصرف اليومي بين اليوان والدولار.
- احتساب السعر النهائي وقت العرض أو الطلب.
- إضافة رسوم المناولة أو الرسوم التجارية المحددة.
- عدم الاعتماد على سعر نهائي قديم مخزن في الكتالوج.
- حفظ السعر المستخدم في الطلب عند تأكيده لأغراض التدقيق والمحاسبة.

### 4. إدارة طلبات العملاء

- تمكين العميل من تصفح الكتالوج.
- إنشاء طلب بحالة مسودة.
- التحقق من SKU والمخزون والكميات.
- تأكيد الطلب بعد استكمال المتطلبات التجارية والدفع حسب السياسة المعتمدة.
- إرسال العملية إلى قناة التكامل لإنشاء مستند ERPNext المناسب.
- متابعة حالة الطلب من السوق دون كشف بيانات موردين أو عملاء آخرين.

### 5. التعامل مع المورد

- استقبال بيانات المنتج والمخزون من المورد أو موظفيه المصرح لهم.
- مراجعة المنتجات قبل نشرها للعملاء.
- فصل بيانات كل مورد عن بيانات الموردين الآخرين.
- الاحتفاظ بسجل تغييرات الأسعار والمخزون والمنتجات.
- إمكانية إضافة فحص جودة أو مستندات المورد في مراحل لاحقة.

## ما لا يقوم به السوق

- لا يمثل النظام المحاسبي ولا يستبدل ERPNext.
- لا يتصل مباشرة بقاعدة بيانات ERPNext ولا يرسل إليها أوامر من مسار HTTP للمستخدم.
- لا ينشئ حساب ERPNext لكل موظف تابع للمورد.
- لا يمنح موظفي المورد صلاحيات ERPNext مباشرة.
- لا يدير الشحن والتتبع الميداني؛ هذه مسؤولية نظام الشحن.
- لا يقرر القيود المالية النهائية خارج قواعد التكامل وERPNext.
- لا يسمح للمورد بالوصول إلى طلبات أو بيانات مورد آخر.

## التكامل مع ERPNext

ينشئ السوق أوامر `Supplier` و`Sales Order` عبر OP-03 وOutbox غير المتزامن. أما موظفو المورد، إن تم دعمهم مستقبلاً، فيستخدمون حسابات داخل السوق مرتبطة بمؤسسة المورد.

يجب ضبط `OP03_GATEWAY_URL` و`MARKET_ERP_KEY` في خادم السوق، وضبط القيمة المطابقة لـ `MARKET_INTEGRATION_KEY` في OP-03. لا يحتاج خادم السوق إلى مفاتيح ERPNext نفسها.

في Docker يجب أن تكون القيمتان متطابقتين في الخدمتين، ولا تُرسل هذه المفاتيح إلى تطبيقات العملاء أو الموردين.

يجب أن يحتفظ النظام بثلاثة أشياء منفصلة:

- سجل المورد المحلي.
- معرّف كيان `Supplier` في ERPNext.
- هوية التكامل المستخدمة من الخادم للوصول إلى ERPNext.

مفتاح API لا يرسل إلى تطبيق المورد ولا يعتبر بديلاً عن التحقق من المستخدم وصلاحياته.

## الحدود الأولية للمشروع

المرحلة الأولى تركز على:

- الموردين المتعاقدين.
- الكتالوج والـ SKU.
- المخزون والأسعار.
- طلبات العملاء.
- مزامنة المورد والعمليات المطلوبة مع ERPNext.
- العزل الكامل بين بيانات الموردين والعملاء.

أما الحسابات المتقدمة لموظفي المورد، والموافقات متعددة المراحل، وتقييم الموردين، وإدارة الوثائق، فتدرج في مراحل لاحقة بعد تثبيت النموذج الأساسي.

## قاعدة بيانات PostgreSQL

قاعدة السوق مستقلة عن قاعدة نظام الشحن وERPNext. لتشغيلها:

```bash
cd database
docker compose up -d
docker compose ps
```

بيانات الاتصال الافتراضية للخادم:

```text
DATABASE_URL=postgresql+psycopg://market_user:marketpass2026@localhost:5543/shipping_marketplace
```

يغطي المخطط الموردين، مستخدمي الموردين، مشغلي السوق، المنتجات، الطلبات، بنود الطلبات، المفاتيح المحلية، اعتماد ERPNext، مهام الربط، أسعار الصرف، وسجلات التدقيق والتغييرات.

> هذا الملف وثيقة تعريفية قيد التطوير، وليس مواصفة تنفيذية نهائية.

## دمج وظائف التجارة الإلكترونية

تم دمج وظيفة تصنيفات المنتجات من مشروع `FastAPI-E-Commerce-Backend` داخل خدمة السوق الحالية بشكل متوافق مع عزل الموردين:

- `GET /api/market/catalog/categories?supplier_id={id}` لعرض تصنيفات مورد.
- `POST /api/market/catalog/categories` لإنشاء تصنيف تابع لمورد.
- `DELETE /api/market/catalog/categories/{category_id}` لحذف التصنيف لموظفي السوق.
- المنتج يمكن أن يرتبط بعدة تصنيفات عبر `category_ids`.
- بيانات الصور تحفظ في `image_urls` كروابط أو مفاتيح Object Storage؛ لا تُخزّن الملفات الثنائية داخل PostgreSQL.

لتطبيق دعم الصور على قاعدة موجودة:

```bash
psql -h localhost -p 5543 -U market_user -d shipping_marketplace -f database/migrations/002_catalog_media.sql
```

لم يتم نسخ نماذج `users` و`products` العامة من المشروع المصدر، لأن السوق يملك نماذج مختلفة لعزل الموردين وربط ERPNext (`SupplierUser`, `MarketOperator`, `marketplace_catalog`).
